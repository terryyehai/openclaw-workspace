**目的**：揭示 Canvas 遊戲自動化的核心難點
**使用者**：Chrome 自動化工具使用者、調試座標問題的人

---

**2. 座標校準流程（Step A / Step B）**
```javascript
// Step A：取得 iframe 實際位置
const rect = gameIframe.getBoundingClientRect();
→ { left, top, width, height }

// Step B：換算公式
x_viewport = iframe.left + (x_ref / 430) * iframe.width
y_viewport = iframe.top  + (y_ref / 932) * iframe.height
```
**目的**：解決「座標點不到」的根本問題
**使用者**：需要動態調整座標的自動化測試

---

**3. 前置準備與 3 步測試流程**
```
Step 1：Login（標準 HTML 表單）
Step 2：Loading Page（Canvas，需座標點擊）
Step 3：Basic Game Play（SPIN、BALANCE 驗算）
```
**目的**：提供最小範圍的 QA 執行流程
**使用者**：快速驗證遊戲基本可玩性

---

**4. 實戰經驗與常見陷阱**
```
✓ iframe 不是佔滿整個 viewport
✓ 座標換算需要 430×932 基準值
✓ get_page_text 無法取得遊戲數值（跨域限制）
✓ javascript_tool 無法存取 iframe 內 DOM
```
**目的**：避免重複踩坑
**使用者**：初次使用 Chrome 自動化測試的人

## 📋 常見問題解答

**Q1：我在寫自動化測試腳本，應該優先看哪個文件？**

A：
1. 先讀 **skill.md** 了解測試模塊、異常處理規則、座標基準
2. 再讀 **CLAUDE.md** 的 RunTest 指令集了解腳本執行架構
3. 在腳本中實現異常處理邏輯（參考 skill.md）
4. 如果遇到座標問題，查閱 **h5-game-qa.md** 的校準方法

---

**Q2：我在進行 Chrome 自動化測試，座標總是點不到，該怎麼辦？**

A：按 **h5-game-qa.md** 的流程：
1. 用 JavaScript 取得 iframe 的 `BoundingClientRect`
2. 用公式換算座標：`x_viewport = iframe.left + (x_ref / 430) * iframe.width`
3. 如果還是不行，用 `zoom` 放大目標按鈕區域，從截圖確認正確座標
4. 永遠不要盲猜座標——先校準再測試

---

**Q3：skill.md 中的座標表是否適用於所有遊戲？**

A：
- **基本適用**：M1、M2、M3 的按鈕位置在大多數遊戲上相同
- **遊戲專屬覆寫**：不同 Game ID 的座標可能略有差異，應在 Excel 腳本的 Config sheet 中覆寫
- **首次測試新遊戲**：先以 SPIN 按鈕做 1 次座標驗證，確認有效後再繼續

---

**Q4：skill.md 的 4 類異常處理是強制要求嗎？**

A：**是的**。根據 CLAUDE.md 的 Subagent 建構規則：
> **異常處理規則（從 skill.md，3 條必帶）**：
> - Timeout Kick：出現警示視窗 → 截圖 → 確認關閉 → 立刻 SPIN 一次
> - Free SPIN 觸發：等待全程完成，BALANCE 驗算涵蓋 Free SPIN 總贏分
> - 活動彈跳視窗：截圖 → 關閉 → 確認回到正常遊戲畫面

---

**Q5：h5-game-qa 提到的「430×932 基準尺寸」是什麼？**

A：
- **430×932**：設計遊戲時的理想手機尺寸（寬 × 高）
- **實際瀏覽器尺寸**：因最小寬度限制，通常變成 ~500×697
- **座標換算基準**：所有參考座標（如 skill.md 中的座標表）都是基於 430×932 來設計的
- **換算公式**：自動化測試時用公式轉換為實際瀏覽器視窗的座標
